## 風險

1. **可觀測性盲區：全天無 Health Record 不會被 chronic 偵測捕捉。** ADR 0001 的慢性故障判定建立在「有失敗事件才分類累計」；若當天 pipeline 整條沒跑完（如 07-07/07-08），連 subject 都不存在，不會被計入任何 subject 的失敗次數，也就永遠不會 escalate。過去 4.5 個月已發生 7 次，目前只能靠人工翻 archive 缺口才會發現。
2. **`quality_alert` 從未觸發過一次（140/140 天皆 false）。** 即使 issue #24 已修正 rubric 飽和問題，新判準上線僅 7 天，尚不足以驗證「該告警時真的會告警」。若這個旗標的門檻本身也偏鬆，換了更有鑑別力的 judge 模型也救不了它。
3. **README.zh.md / README.md 與實際設定不同步。** README 仍寫 judge 預設模型為 `google/gemma-4-e4b`，但 CLAUDE.md 與 issue #24 已確認實際預設為 `qwen3.6-35b-a3b`（原模型因分數飽和已汰換）。這種「單一事實來源」（CLAUDE.md）與周邊文件（README）不同步的漂移，若持續累積會侵蝕「倉庫即記錄系統」這條核心工程理念的可信度。
4. **單點依賴**：pipeline 綁定單一本機 LM Studio 實例（`localhost:1234`）與單一 cron 排程機器；`load_model.py`/`main.py` 的兩段式喚醒設計已考慮模型冷啟動風險，但機器本身（電力、網路、硬體）仍是唯一執行環境，沒有 fallback。此為已知、可接受的個人專案取捨，非新風險，僅記錄供追蹤。
5. **Backlog 治理债**：#2、#3 缺 triage 標籤超過三個月，若不處理，往後新開的 issue 也可能沿用「不 triage」的慣性，稀釋掉 triage-labels 文件原本要建立的紀律。
